Reliable data transfer is an important problem in computer networks because UDP itself does not guarantee delivery, ordering, or protection from duplicate packets. A sender using UDP can transmit data quickly, but a packet may be lost before reaching the receiver, and an acknowledgement may also be lost on its way back. To make the transfer dependable, our program adds reliability at the application layer instead of relying on UDP to provide it.

The file is not transmitted as one large block. The sender reads the input file in chunks of 512 bytes and places each chunk inside a packet structure. Every packet contains a sequence number, the number of useful data bytes, a flag indicating whether it is the final packet, and the actual file data. This allows a large file to be divided into manageable pieces and reconstructed correctly by the receiver.

The Stop-and-Wait protocol allows only one unacknowledged packet at a time. The sender begins with sequence number zero and sends the first packet. After sending it, the sender waits for the corresponding acknowledgement. If ACK0 is received, the sender changes the sequence number to one and prepares the next chunk. After ACK1 is received, the sequence number returns to zero. Therefore, the sequence numbers alternate between zero and one during the complete transfer.

Timeouts are necessary because the sender cannot wait forever for an acknowledgement. After transmitting a packet, the sender waits for a limited amount of time. If no acknowledgement arrives within the timeout period, the sender assumes that either the data packet or its acknowledgement was lost. It then retransmits the same packet instead of moving to the next part of the file.

Sequence numbers also allow the receiver to detect duplicate packets. For example, suppose packet zero reaches the receiver successfully but ACK0 is lost. The sender eventually times out and sends packet zero again. However, the receiver is already expecting packet one. It therefore recognizes the new copy of packet zero as a duplicate, avoids writing its data to the output file again, and resends ACK0. This prevents duplicated content from appearing in the reconstructed file.

The receiver creates an output file and waits for UDP packets on a fixed port. Whenever the expected packet arrives, it writes only the valid number of bytes specified by the packet's data length. It then sends an acknowledgement containing the packet's sequence number and changes the sequence number it expects next. When a packet marked as the final packet arrives, the receiver knows that the complete file has been transferred and can close the output file.

Testing is important because successful packet exchange alone does not prove that a file was transferred correctly. After the transfer, the original input file and the reconstructed output file can be compared byte for byte. If they are identical, the program has successfully preserved all data during transmission. Additional tests can deliberately delay the receiver, cause acknowledgements to be lost, or use files of different sizes to verify that timeout, retransmission, duplicate detection, and file reconstruction work correctly.

This small project demonstrates how reliability mechanisms can be built on top of an unreliable transport protocol. Although Stop-and-Wait is simple and easy to understand, it can be inefficient because the sender must wait after every packet. More advanced protocols such as Go-Back-N and Selective Repeat improve performance by allowing multiple packets to be outstanding at the same time while still using acknowledgements, sequence numbers, and retransmissions to achieve reliable communication.
